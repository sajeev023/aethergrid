## 1. Executive Summary
AetherGrid has undergone a comprehensive, end-to-end security, architectural, and operational hardening audit. ## 2. Architecture
AetherGrid operates as a zero-trust distributed storage marketplace and orchestration layer:
- **Control Plane**: Next.js 15.5 App Router + Node 24 native `node:sqlite` in WAL mode (`data/aethergrid.db`).
- **Physical Node Layer**: Standalone Node.js storage daemon (`node-client/node-daemon.mjs`) communicating outbound over HTTPS via Bearer token authentication.
- **Dedicated Volume**: Dedicated mount at `D:\AetherGridStorage` isolated from the Windows OS drive `C:`.
- **Single-Node Beta Mode (`BETA_SINGLE_NODE_MODE=true`)**: Honestly discloses 1x primary storage during initial bootstrap while preserving 2x replication capabilities for when community nodes join.

## 4. Security Audit
- **Path Traversal Defense**: Passed. Chunk hashes are strictly validated against `/^[a-f0-9]{64}$/`. Traversal payloads (`../../secret.txt`, `..\..\Windows\System32`, `%2e%2e%2f`) are unconditionally rejected prior to filesystem operations.
- **Canonical Boundary Check**: `assertPathInsideStorageRoot()` verifies that normalized target paths have `D:\AetherGridStorage\chunks\` as an immutable prefix.
- **Atomic Failure Rollback**: Partial uploads that fail midway are automatically rolled back, deleting any partially written chunks from disk and database records.

---

## 5. Authentication Audit
- **Node Authentication**: Node daemons authenticate strictly via SHA-256 token hashes sent in `Authorization: Bearer <token>` or encrypted payload. Node identity is derived server-side from the verified token record; client-provided node IDs are never trusted blindly.
- **User Authentication**: Salted bcrypt password hashing (cost factor 10) + JWT sessions signed with HS256 (`jose`) stored in `HttpOnly`, `SameSite=Lax` cookies.

---

## 6. Authorization Audit
- **Multi-Tenant Isolation**: Verified. Every object request (`/api/taker/files/[id]`) strictly enforces `file.user_id === session.userId`.
- **IDOR Protection**: Automated tests proved that User B (Eve) cannot read, inspect, or delete User A's (Alice's) files, receiving HTTP 403 Forbidden.
- **Admin Authorization**: Access to `/admin` and `/api/admin/*` is locked down in `middleware.ts` by checking `payload.roles.includes('ADMIN')`.

---

## 7. Encryption Audit
- **Algorithm**: Authenticated AES-256-GCM.
- **Nonces/IV**: Cryptographically secure 12-byte random IV per chunk generated by `crypto.randomBytes(12)`.
- **Integrity**: 16-byte GCM authentication tag verified during decryption.
- **Checksum**: Whole-file SHA-256 computed on upload and verified upon download before streaming to the client.
- **Zero-Plaintext Guarantee**: Storage provider disks store only opaque `.chunk` binary blobs; providers cannot access customer plaintext.

---

## 8. Payment Audit
- **Server-Side Activation**: Front-end payment clicks never activate subscriptions. Subscriptions are activated exclusively via `/api/payment/webhook`.
- **Cryptographic Verification**: Webhooks enforce HMAC SHA-256 signature verification against `PAYMENT_WEBHOOK_SECRET`.
- **Idempotency**: Webhook events are logged in `payment_transactions`. Replay attacks and duplicate webhooks are detected and bypassed.

## 9. Database Audit

- **Concurrency**: WAL mode (`PRAGMA journal_mode = WAL`) and `PRAGMA synchronous = NORMAL`.
- **Foreign Keys**: Enabled (`PRAGMA foreign_keys = ON`).

## 10. Backup & Recovery
- **Snapshot Engine**: `scripts/backup-db.mjs` executes atomic online SQLite backups via `VACUUM INTO '<backup_path>'`.
- **Manifest**: Each snapshot generates a signed JSON manifest with timestamp and SHA-256 checksum.
- **Restoration Test**: `scripts/restore-db.mjs` successfully verified and restored from backup snapshots, verifying all 7 core tables.

---

## 11. Node Reliability
- **Heartbeat Cadence**: Every 15 seconds.
- **Timeout Policy**:
  - `0s – 30s`: Healthy `ONLINE`
  - `30s – 90s`: `SUSPECTED_OFFLINE`
  - `> 90s`: `OFFLINE`
- **Failover Logic**: When a primary node drops, the orchestrator automatically routes requests to the surviving replica node (`X-AetherGrid-Failover-Used: true`).

---

## 12. Capacity Management
- **Hierarchy**:
  1. Physical Drive Free Space (verified via `fs.statfsSync`)
  2. Safety Threshold (`AETHERGRID_RESERVED_FREE_SPACE_GB=10`)
  3. Configured Node Capacity (50 GB)
  4. Quota check against user subscription
- **Safety Rejection**: Allocations are blocked with `STORAGE_CAPACITY_EXHAUSTED` if free space nears the reserve threshold.
